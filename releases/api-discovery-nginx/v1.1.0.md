## What changed

|  | 1.0.0 | 1.1.0 | |
|---|---|---|---|
| **Download size** (compressed) | 2840 MB | **288 MB** | −90% |
| On-disk size (extracted) | 5.06 GB | **1.01 GB** | −80% |

### Why it was 5 GB

The image bundles PyTorch for its autoencoder and LSTM anomaly-detection models. Installing `torch` from the default PyPI index pulls the **CUDA build**, which drags in the entire NVIDIA GPU runtime as transitive dependencies:

| Package | Size |
|---------|------|
| `nvidia-cublas` | 423 MB |
| `nvidia-cudnn-cu13` | 366 MB |
| `nvidia-cufft` | 214 MB |
| `nvidia-nccl-cu13` | 206 MB |
| `nvidia-cusolver` | 201 MB |
| `triton` | 198 MB |
| `nvidia-cusparselt-cu13` | 170 MB |
| 10 more `nvidia-*` packages + `cuda-toolkit` | remainder |

This project only ever runs **CPU inference**. None of that GPU runtime was ever executed — it was pure download cost for every user.

### The fix

The build now resolves PyTorch from the CPU-only wheel index:

```dockerfile
RUN pip install --no-cache-dir --target=/deps \
      --extra-index-url https://download.pytorch.org/whl/cpu \
      -r requirements.txt
```

Dependency resolution drops from **29 packages to 10**. Every `nvidia-*` package, `triton`, and `cuda-toolkit` disappears. `torch 2.13.0` becomes `torch 2.13.0+cpu`.

A build-time assertion now fails the build if a CUDA wheel ever creeps back in, so the regression cannot ship silently.

`pytest` was also removed from the production image.

The `gcr.io/distroless/python3-debian12` base image was refreshed to pick up upstream security patches.

## Upgrading

No configuration changes. Pull and restart:

```bash
docker pull gusgh13900/api-discovery-nginx:1.1.0
docker pull gusgh13900/api-discovery-agent:1.1.0
```

- Your `/app/output` volume is fully compatible — SQLite database, trained models, and user accounts carry over untouched.
- Existing trained models (`autoencoder.pt`, `lstm_autoencoder.pt`) load unchanged; they were already stored as CPU tensors.
- `1.0.0` remains on Docker Hub if you need to roll back.

## Verified

- `torch 2.13.0+cpu`, `torch.cuda.is_available() == False`
- Tensor operations and model-manager import working
- Both existing checkpoints load successfully
- `GET /healthz` returns `200 {"status":"ok"}` within 4 seconds of container start
- Login page renders
- End-to-end ingestion from agent to dashboard confirmed (`POST /api/ingest` → `200 OK`)

## Known issue

The dashboard still creates a default `admin` / `admin1234` account on first start. **Change the password immediately after deploying.** A future release will generate a random password and print it to the container log instead.
